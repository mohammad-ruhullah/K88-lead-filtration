# AGENTS.md

## Project Objective
Build a Vite + React + TypeScript + Tailwind web app that:
1) runs DuckDB-Wasm in the browser,
2) loads user-selected very large CSV files (4+ files supported),
3) filters data based on user criteria,
4) produces one final merged dataset using UNION semantics,
5) exports result without server-side processing.

## Non-Negotiable Constraints
- All data ingestion, filtering, union, and export must run in the user's browser.
- Prioritize efficiency and memory safety for million-row CSV inputs.
- Do not send dataset rows to any backend service.

## Huge File Safety Disclaimer (MANDATORY)
- DO NOT EVER TRY TO READ THESE FILES FULL.
- For inspection/debugging, only read tiny slices (e.g. first 5-50 lines).
- Use small previews only (`Read` with low limit or `head -n` style command).
- Never run commands that print full file contents.
- In app code, avoid loading full CSV content into JS strings/arrays when file handles can be registered directly with DuckDB-Wasm.

## Source Datasets (Current)
- User will pick files from local machine at runtime (do not assume fixed filesystem paths).
- Current sample files used during development:
- `From_500_To_Beyond_1_of_4.csv`
- `From_500_To_Beyond_2_of_4.csv`
- `From_500_To_Beyond_3_of_4.csv`
- `From_500_To_Beyond_4_of_4.csv`

## Confirmed Data Strategy
- Combine datasets with UNION (not JOIN).
- Default union operator: `UNION ALL BY NAME` to preserve all rows and tolerate schema drift.
- Support dynamic number of input files (not fixed to exactly 4).
- If deduplication is later required, add an optional dedupe stage as a separate feature.

## Architecture Direction
- DuckDB-Wasm service layer for:
  - instantiate DB/worker once,
  - manage a single long-lived connection,
  - register user-selected local CSV file handles,
  - execute SQL queries for filtering/union,
  - export result files via `COPY ... TO` + `copyFileToBuffer`.
- React UI layer for:
  - file status,
  - filter builder,
  - query preview,
  - export action.
- SQL-first data pipeline (push filtering and union into DuckDB, not JS loops).

## Iterative Feature Roadmap
1. Foundation: DuckDB service + lifecycle states.
2. File registration: load N CSV file handles from file picker and validate schema/header.
3. Filter model: typed criteria and SQL generation.
4. Union pipeline: create merged filtered result table/view.
5. Preview: sampled result rows and row counts.
6. Export: download final merged dataset as CSV.
7. Performance hardening: memory/thread tuning, cleanup, and UX improvements.

- 2026-08-24: Reworked the filtration rules to be **owner-centric** instead of property-centric (client requirement). Seven confirmed rules:
  1. **Claim gate runs first** - only `NUMBER_OF_PENDING_CLAIMS = 0` AND `NUMBER_OF_PAID_CLAIMS = 0` survive. NULL/unparsable counts as claimed.
  2. **Owner identity** = exact `OWNER_NAME` + exact address (`OWNER_STREET_1/2/3`, `OWNER_CITY`, `OWNER_STATE`, `OWNER_ZIP`, `OWNER_COUNTRY_CODE`). Normalisation is trim + uppercase + whitespace-collapse only; parts joined with `chr(31)` so values cannot bleed across fields.
  3. **One property with several co-owners is left as-is** - those rows are never merged or collapsed.
  4. **Small properties ride along** - a qualifying owner exports *all* their properties, nothing dropped for being small.
  5. **Airtable dedupe runs BEFORE summing** - an already-worked property cannot help an owner reach the threshold.
  6. **Rows without a street address are dropped**, so unrelated same-name people can never collapse into one bogus owner group.
  7. **Output is grouped** - an owner's properties occupy consecutive rows, richest owner first.
- 2026-08-24: Owner totals sum over **DISTINCT `PROPERTY_ID`**, not rows. A jointly held property emits one row per co-owner sharing a `PROPERTY_ID`, so summing rows would invent money that does not exist. Verified: 92 owner-groups in a single 60MB slice have a repeated `PROPERTY_ID`.
- 2026-08-24: Pipeline is now three statements - `eligible_rows` (one CSV pass: all row-level gates + anti-join), `owner_totals` (distinct-property aggregation), `merged_filtered_dataset` (threshold + ordering). The CSVs are still parsed once.
- 2026-08-24: Replaced the dedicated non-cash re-scan with a single conditional-aggregate funnel query (`total / skipped_claimed / skipped_no_address / skipped_non_cash`), removing a full extra scan of every CSV.
- 2026-08-24: Export re-states `ORDER BY` inside the `COPY` (a materialised table does not guarantee scan order) and adds `OWNER_GROUP_ID`, `OWNER_GROUP_PROPERTY_COUNT`, `OWNER_GROUP_TOTAL` alongside all 25 original columns. Internal `__`-prefixed columns are excluded.

- 2026-08-25: Two rejection reasons were previously **never counted at all**: rows removed by the Airtable dedupe, and rows removed because their owner's total fell under the threshold. The threshold bucket turned out to be the single largest reason in the dataset (111,131 of 283,616 rows - 39% - on the verification slice).
- 2026-08-25: The report is built on a **reconciliation invariant**: `rows scanned - sum(all reasons) === qualified`. Reasons are mutually exclusive because every `FILTER` is conditioned on passing all *prior* stages. The panel renders a `Reconciled` / `Mismatch` badge and, on mismatch, an explicit warning that the counts are unreliable - a silent wrong number is worse than a visible one.
- 2026-08-25: `funnelSQL` now evaluates each predicate exactly **once per row** in a `flags` subquery, then aggregates over the booleans. Repeating the predicates inside a dozen `FILTER` clauses would re-run `regexp_matches` a dozen times per row across millions of rows.
- 2026-08-25: The report's CRM check uses `EXISTS`, **not** a `LEFT JOIN`. Verified: with a duplicated `(PROPERTY_ID, OWNER_NAME)` pair in the lookup, a `LEFT JOIN` reported 283,617 scanned rows against a true 283,616, while `EXISTS` stayed correct. `createAirtableLookupSQL` also now builds the lookup with `SELECT DISTINCT` to remove the hazard at source.
- 2026-08-25: Split the policy builders into their individual predicates - `buildPropertyTypeFilterParts()` (`propertyTypePolicy.ts`) and `buildClaimGateParts()` (`ownerGroupingPolicy.ts`). The existing `build*SQL` functions now compose from those parts, so the report's attribution can never drift from the filter that is actually applied. Verified the refactored cash-only filter is **identical on all 283,616 rows** (0 disagreements) against the original expression.
- 2026-08-25: Report cost is **no extra pass over the CSVs**. The funnel query already scanned once; the threshold and owner-level counts run on the already-materialised `eligible_rows` / `owner_totals` tables.

Note 229 rows are caught **only** by the securities-evidence cross-checks after passing the property-type test - previously invisible inside the non-cash lump.
- 2026-08-25: `FunnelStats` was replaced by `FiltrationReportData`; the four summary tiles now derive from the same report object via `summarise()`, so tiles and report cannot disagree.

- 2026-08-30: Added the **individual-owner-only rule** (client requirement: "only person data"). The source CSV has no owner-type column, no business flag and no first/last split, so the only signal is `OWNER_NAME` itself. New always-on stage, generated by `src/services/ownerEntityPolicy.ts`, applied as stage 4 - after the cash-only rule, before the Airtable dedupe.
- 2026-08-30: Stage placement is **arithmetically neutral for surviving individuals**. Owner identity is `OWNER_NAME` + full address, so an entity name and a person name can never share an owner group; the rule removes whole owner groups, never a slice of one. Verified: the surviving individual groups keep identical totals and property counts. What does change is report attribution, `DENSE_RANK()` group-ID renumbering, and the owner-level counts. Slot 4 was chosen so the previously logged claimed / no-address / non-cash numbers stay comparable line-for-line, and so "Already in Airtable" keeps meaning *a lead we already worked* rather than *an entity we would never have worked*.
- 2026-08-30: Detection is **two-tier and purely negative** - it rejects on evidence of an entity and never requires proof of personhood. A given-name allowlist was rejected as a design: it would silently delete uncommon, immigrant and transliterated names (`KOBZEFF CONSUELO`, `SINGH JASBIR`, `NG MARINA KWA K`, `SUN HUEI C`) - exactly the leads nobody else is calling. The cost asymmetry drives this: a false positive is a permanently lost paid-for lead, a false negative is one wasted phone call.
  - **Tier A** (276 keywords, hard reject): head nouns naming what an organisation *is*. Modifiers (`american`, `first`, `national`) are deliberately excluded - redundant, because the head noun catches the name anyway, and pure added risk.
  - **Tier B** (8 keywords, rescuable): `co bank banks church churches temple lodge union` - real entity volume but also real surnames. Rejected only when the name does not read as a person: keyword must sit in token position 0 or 1, at most 4 tokens, no digits, no organisation-context word (`BANK AMERICA N A`), and no second Tier-B keyword (`UNION STAMPING CO`).
- 2026-08-30: Matching uses a **space-padded normalised name**, not word-boundary regex. DuckDB is RE2: no lookahead/lookbehind, and `\y` is PostgreSQL-only. `' ' || trim(regexp_replace(lower(name), '[^a-z0-9]+', ' ', 'g')) || ' '` gives exact whole-word matching by construction and folds `L.L.C.` to `l l c` and `C/O` to `c o` on the way. The normalised name is materialised once per row in a scan CTE (`__owner_norm`, and `owner_norm` in the funnel) because the entity predicate reads it six times.
- 2026-08-30: **Occupational and place words are banned from the keyword lists** - they are overwhelmingly surnames or given names in this data. Measured row counts on the verification slice: `loan` 114 (`NGUYEN LOAN T`, `CHU LOAN K` - common Vietnamese given name), `young` 635, `king` 428, `park` 389 (Korean surname), `hall` 330, `dean` 228, `st` 226 (`ST JOHN B`), `marshall` 214, `sun` 173, `house` 150, `bishop` 105, `glass` 90, `love` 79, `best` 71, `rich` 61, `marina` 69, `field` 60, `abbott` 45, `pa` 45, `cable` 44, `chapel` 28, `grill` 24, `bonds` 14, `parish` 8 (all 8 are people), plus `mart`/`market`/`music`/`records`. A set-intersection assertion in the validation harness fails if any of these ever leaks into `ENTITY_HARD_KEYWORDS` or `ENTITY_SOFT_KEYWORDS`.
- 2026-08-30: Verified against real data (60MB window at byte offset 80MB of `From_500_To_Beyond_1_of_4.csv`, 284,171 rows, keyword lists parsed straight out of the TypeScript module so harness and shipped SQL cannot drift). Of **116,341 rows eligible** after the claim, address and cash-only gates: **18,493 rejected by Tier A (15.90%)**, **681 by Tier B (0.59%)**, **97,167 kept as individuals (83.52%)**. Owner level: 113,892 groups formed, **63 reach $5,000, of which 13 are entities and are removed, leaving 50 individual owners** - the rule removes roughly a fifth of the qualified owner list.
- 2026-08-30: **`AUSTIN DIAGNOSTIC` - the largest owner group cited in the 2026-08-24 verification above (19 properties, $29,205) - is an entity and is now excluded.** Any regression comparison against that logged number must account for this.
- 2026-08-30: False-positive audit: every rejected name of 3 tokens or fewer with no digits and no `&` (the shapes most likely to be a person) was dumped and eyeballed - 400 names, **all genuine businesses, zero real individuals** (`JAWS TECHNOLOGY`, `EASTLAND ESCROW`, `IQUE INC`, `MONARCH ESCROW`, `RAMIREZ CONST CO`). - 2026-08-30: **Known and accepted false negatives** - businesses whose head noun is not in the list, or that the Tier-B rescue lets through: `PREFERRED BANK`, `FLAGSTAR BANK FSB`, `ECONO LODGE`, `POOLMART CO HQ`, `CABO GRILL`, `SANTA CLARA PARISH`, `ALL AUTO GLASS`, `RYAN WILLIAMS BAIL BONDS`. Tightening the Tier-B rescue to token position 0 only would catch several of these but would kill `KEEFER TEMPLE T`, a real person. Keeping the person wins.

The generated SQL was compiled straight out of the four policy modules and executed against a 200,000-row slice via the `duckdb-async` Node binding, reproducing the whole pipeline: `eligible_rows` (with the new `scanned` CTE and `EXCLUDE (__owner_norm)`), `owner_totals`, `merged_filtered_dataset`, the export `COPY`, and `funnelSQL`.
